(`src/fork/**`, `drizzle.fork.config.ts`, `scripts/fork/**`, `app/api/fork/**`, `.github/workflows/fork-*.yml`, ...).

## Flags (all default off; only the literal `true` enables)
`FORK_STACKS_ENABLED`, `FORK_ARCANE_ENABLED`, `FORK_MIRRORS_ENABLED`. Pre-migration dump: `FORK_MIGRATE_DUMP=auto|required|off`. Arcane URL allow-list: `FORK_ARCANE_NET_ALLOWLIST` (default empty = deny, see below). Discovery interval: `FORK_DISCOVERY_INTERVAL_MINUTES` (default 15, 5–1440, ±20 % jitter, operator-only). Materializer drift/probe tick: `FORK_MATERIALIZE_TICK_SECONDS` (default 60, 5–3600, operator-only).

## Single-tenant requirement (D21, ADR-011) and fork secrets (D23)
The fork refuses to configure itself unless the instance is single-tenant: exactly one organization, `AUTH_SIGNUP_ENABLED=false`, no agent/storage channel used by fork rows bound to another organization.
Set `AUTH_SIGNUP_ENABLED=false` (upstream default is `true`; with it `false` NO new account can be created, not even by an admin) and keep `MCP_ENABLED=false` (advisory).
On failure the fork *locks configuration only* (activated schedules, finalisation, drift job and notifications keep running): `/api/fork/status` carries the banner text; an audit event + one pending notification record are written per state change.

**Fork KEK:** `${PRIVATE_PATH}/keys/fork-kek/` (`<kid>.key` 0600 + `active`), generated on first use, separate from the master key. **Back it up together with the database** — fork secrets (Arcane API keys) are unreadable without it, and a DB dump alone does not contain it.
Audit retention: `FORK_AUDIT_RETENTION_DAYS` (default 400, floor 90).

## Arcane connection (W05)
Read-only discovery source. Code: `src/fork/arcane/` (client, schemas, key policy, connection service), `src/fork/discovery/provider.ts` (`DiscoveryProvider`, 8 methods), `src/fork/net/` (SSRF guard, IP-pinned GET transport, rate limiter), `src/fork/actions/arcane-connection.action.ts` (server actions: save / test / rotate key / disconnect). Design + threat mapping: vault `ADR/ADR-012-arcane-connection-ssrf`, `ADR/ADR-002-arcane-compat`.

- **Key = list permissions only, environment-scoped** (`environments:list` global; `projects|containers|volumes|networks|images:list` per environment). Any `*:read`, any write class or a global grant of an env-scoped permission is refused with the exact names; `projects:read` is an opt-in per connection (tier 2). Arcane's `*:read` returns env values / volume bytes / env-file bytes.
- **URL guard, default deny.** `https://` anywhere that resolves to public addresses. Loopback / private / link-local / ULA need the operator allow-list `FORK_ARCANE_NET_ALLOWLIST` (comma list of IPs, CIDRs, host names; empty = deny; env-only, never settable from the UI). `http://` only for allow-listed private addresses (lab: `FORK_ARCANE_NET_ALLOWLIST=127.0.0.1`). Cloud metadata addresses (169.254.169.254 …) are never allowed. The host is resolved once, every answer must pass, and the request connects to that vetted address (DNS-rebinding defence). Redirects are never followed. TLS verification is on; the per-connection opt-out is audited.
- **Changing host, port or scheme of the URL requires typing the key again** (SEC-10): a stored key is never sent to another endpoint.
- Connection actions are system-admin only, refused while the single-tenant self-check fails, rate limited (6/min per user), audited (`fork.arcane.connection.{save,test,rotate_key,disconnect}`), and never return, log or audit the key.
- Tests: `pnpm test:fork` (fake Arcane over real HTTP + Postgres). Live lab test: `cd dev/fork-lab && docker compose --env-file .env.lab -f compose.arcane.yml up -d arcane` (+ demo stack), then `FORK_LAB=1 pnpm test:fork arcane-live` (lab admin login only mints/deletes scoped keys).

## Discovery sync (W07)
Reads the inventory of every **enabled** Arcane environment into versioned, provenance-tagged `StackInventory` rows (`fork_stack` + `fork_stack_inventory`). Read-only against Arcane (GET only, the W05 client), **no secret value is ever stored**: the client drops env values at the boundary, the normaliser builds the inventory field by field from an allow-list (compose labels + the three D18 hint keys only; no command lines, no raw labels, no file contents), and the strict schema rejects anything else. Design: vault `ADR/ADR-004-stack-recoverypoint-model` §10, `Waves/W07-discovery-sync`.
Code: `src/fork/inventory/{normalize,labels,compose-yaml,schema}.ts` (pure normaliser, hint grammar, SEC-17 YAML limits, schema v1), `src/fork/discovery/{sync,sync-state,sync-summary}.ts` (orchestrator, lease/breaker/reconcile/write path), `src/fork/cron.ts` (cron on the runtime **config** plane — no upstream hook), `src/fork/actions/sync.action.ts` ("Sync now").
- **Trigger:** cron tick every 60 s, due when `now − last_sync_attempt_at ≥ interval × (0.8…1.2)` (persisted ⇒ a missed run is one catch-up, never a backlog); "Sync now" (system admin, `arcane.manage` resource-scoped, D21 gate, 6/min, audited). Mode machine (ADR-010): the cron is started only in mode `on` and every tick re-checks it — `locked`/`off` ⇒ no discovery (activated schedules in the runtime plane are unaffected).
- **ARCH-10:** one DB lease per connection (`fork_lock` `sync:<id>`, TTL 5 min, renewed per environment, stolen only after expiry) ⇒ overlap = skip (no queue), replicas safe. Circuit breaker (persisted): 5 consecutive connection-level failures open it, back-off 5 min × 2^(n−5) capped at 60 min; the cron skips while open, the first attempt after the back-off is the half-open probe, "Sync now" is always allowed and a success closes it. Opening records one pending notification (`discovery.circuit_open`, delivery W13).
- **Per run:** preflight (version pin, key permission self-test — a key that gained any `*:read` is refused —, environment list) → reconcile environments (newly covered ⇒ row `enabled=false`; no longer covered ⇒ marked, its stacks `stale_since`, cache kept) → per enabled environment (60 s budget): containers, volumes, networks, images, projects → normaliser → ONE transaction (stack upsert, new inventory version **only when the content hash changed**, `stale_since` cleared, unseen stacks `absent`, keep the newest 30 versions + any referenced by a recovery point). Failure ⇒ cached inventory kept and marked stale; the environment shows the code-only reason.
- **Untrusted input (SEC-22):** labels give hints (enum/boolean grammar, invalid values ignored), never identity or authority; paths must be absolute, no `..`, no control characters; a project label that is not a valid identity rejects that stack only; limits (500 services, 2000 mounts, 1 MiB) reject, never truncate. **Tier 2** (opt-in `projects:read`): compose text is parsed under SEC-17 limits (256 KiB, depth 24, 20 000 nodes, ≤ 10 aliases, no custom tags, no duplicate keys) and reduced to service names, env **key names**, env_file paths, profiles; a refused file leaves `compose_read: "none"` + a warning.
- `stop` / `exclude` / `consistency` hints are recorded as data; **R1 never stops containers** (D29).
- Tests: `pnpm test:fork normalize` (+ `w07-*`: normaliser fixtures, SEC-17, sync/ARCH-10/breaker, all-table canary, contract vs the pinned Arcane spec, static guards). Live lab test (demo stack must be discovered): `cd dev/fork-lab && docker compose --env-file .env.lab -f compose.arcane.yml up -d arcane && docker compose -f demo-stack/compose.yml -f demo-stack/compose.override.yml up -d db web` (NOT `seed.sh`: it rewrites tracked `uploads/`), then `FORK_LAB=1 FORK_TEST_DATABASE_URL=… pnpm test:fork discovery-live`.
- Not in W07: coverage/completeness (W09), reading file contents (W09/W10), keeping environment settings across disconnect/reconnect (follow-up), per-connection interval setting in the UI.

## Completeness, protection state and the Configuration tab (W09, M1 gate)
Read-only. Stack details gain a **Configuration** tab, a **Backup blockers** panel on Overview and the derived **protection state** (REVISED-PLAN §4.6). Nothing writes: no migration, no mutation route, no action (the two resolve buttons are `aria-disabled` with a visible reason). Design: vault `Waves/W09-completeness-config-tab`, `Implementation/plan-W09`, ADR-004 §12.
Code: `src/fork/completeness/{types,rules,validate,precedence,facets,view}.ts` (pure, no I/O — a static test enforces it), `src/fork/stacks/protection.ts` (the only DB reader: policy, recovery points, `allowed_path_roots`), `src/fork/ui/stacks/config-tab/*`, copy in `src/fork/ui/labels.ts`.
- **Validator** (`validateCompleteness(inventory, ctx)`): one item per *required* resource (compose files, env files, binds, named/anonymous volumes, recognised databases, locally built images, external networks/dependencies) with status `captured | missing | inaccessible | unsupported | external | excluded | accepted_exclusion | unknown` and a reason code (sentence in `labels.ts`). `complete` is true only when nothing is missing/inaccessible/unsupported/unknown. Compose not read (tier 1) ⇒ env files are `unknown` ⇒ never complete. A DB saved only by file copy is a gap (D29). Paths are re-validated (absolute, no `..`, no control chars, deny list, `allowed_path_roots`); docker socket / system paths / privileged / host network are informational *directives* (§4.4).
- **Primary state** (`derivePrimaryState`): Failed > Partial > Stale > Kit not verified > Awaiting first backup > Protected > Unprotected. Protected needs an active policy, ≥ 1 **verified** recovery point (D43; `pending_verification` = "Backed up · verifying", never counts), no gap and a verified kit. "Partial" needs backup intent (active policy or any RP): a stack nothing is configured for stays Unprotected and shows its gaps as blockers.
- **Facets 1–7 + locked** (`deriveFacets`): last good backup (verified only), test-restore age, deletable from source host (not checked fails closed), host compromise (facet, never Partial), consistency per member, paused after re-authorisation, inventory stale, configuration locked.
- **Inputs not fed yet are "unknown", never invented:** coverage + agent probes (W10), accepted exclusions (W11, modelled, no UI action), kit state (W14, so `false`), channel deletion checks (F4), schedule interval (so never Stale), test-restore age (R2). Until W10 every discovered stack has gaps and nothing can show Protected.
- **Browser DTO** (`completeness/view.ts`): strict, names/paths/statuses/reasons/hashes only. Env variable **names** per service only when compose was read; values are never stored, so no field exists for them. No download control, no content route.
- Tests: `pnpm test:fork w09` (validator fixtures = plan §14 rows 1–7, 21 precedence pairs + exhaustive grid, facets, labels coverage, component + axe + keyboard, static guards), integration on Postgres 17 `w09-protection`, e2e on the real build `w09-config`, live lab `FORK_LAB=1 pnpm test:fork w09-lab`.
- Known tier-1 limits (found live): a locally built image and a privileged container are not visible in Arcane's list (repo digest is set even for local builds on the containerd image store; the list has no `privileged`); an agent probe (W10) or compose `build:` (tier 2) closes them. A deleted `.env` / unreadable bind is invisible before the W10 probe: it shows as "not covered".

## Materializer: stack → ordinary Portabase sources (W10)
A stack is protected by **ordinary Portabase sources** in a stack-owned Project `stack:<environment>/<stack>` (no cron, no retention, no upstream policy of any kind — D30/D33). Code: `src/fork/materialize/` (pure `plan.ts`; `apply.ts` / `remove.ts` services; `drift.ts` job; `context.ts` feed into the W09 views), `src/fork/upstream/` (**copy-and-own adapter, D31**: the only fork code that touches upstream tables; session-free copies of source create/update/remove, project create, storage policy, effective-policy read/revert, credential encryption, agent ACL; pinned by `w10-upstream-contract.test.ts`, which runs on every W-SYNC), migration `0004_stack_sources` (`fork_stack_source`, policy `selection` / `storage_channel_ids` / `applied_plan_hash` / `materialize_state`), server actions `materialize.action.ts` (apply, confirmed remove). The wizard that calls them is W11.
- **Plan** (`planStack`): compose directory → ONE `files` source (snapshot/restic default) covering compose files, env files, the implicit `.env` and every bind under it · other bind → `files` · named volume → `docker-volume` (**SEC-24**: `^[A-Za-z0-9][A-Za-z0-9_.-]+$`, present in the inventory, local driver; path-like / hash-named / external never; **`container_name` is never set**, D29) · database service with a dump input → engine source (host = operator-chosen unique alias; DB data volumes are not also copied) · SQLite → upstream `sqlite` source on an explicit path (never `/var/lib/docker/**`) · manual sources only inside `allowed_path_roots` (D19). `exclude` hints are defaults, explicit selection wins (D18).
- **Apply**: system admin only (`stacks.backup.manage`) **and** the upstream-equivalent agent ACL (org owner/admin of the agent's organization), refused while the D21 gate is locked, rate limited, audited (`fork.materialize.*`), one transaction under a per-stack lock, **idempotent** (same plan ⇒ no writes), **never deletes** (a source the plan no longer wants becomes `orphaned`). Gates: environment mapped to an agent, agent ≥ `FORK_MIN_AGENT_FOR_STACKS` (1.24.0), storage channels usable by the organization. DB passwords go from the input straight into the upstream-encrypted config — never into `fork_stack_policy`, the audit or the result.
- **Remove** needs `confirm:true` and only removes sources that never ran (a backed-up source is refused: deleting it would purge restore data, W12/W14).
- **D39**: `assertEncryptionForActivation(db)` is what W11 calls before activation; an ACTIVE policy while `setting.encryption = false` is a stack blocker ("Backup encryption is switched off…").
- **Drift job** (`FORK_MATERIALIZE_TICK_SECONDS`, default 60; runtime plane — keeps running when configuration is locked): reverts to NULL any cron on a member or on the stack Project and any retention row of a member or the Project (change seen + revert audited); flags structural edits (removed / moved / re-typed / re-configured members, a per-source storage policy, a changed Project channel set, SEC-24 re-check) as blockers that clear when the live row matches again; inventory change ⇒ `inventory_changed`; vanished resources ⇒ `orphaned`. No upstream lock (P08 is not in v1): the revert is the control.
- **Poll guard (CH-22c) with an unchanged agent**: docker-volume members are created only when the agent has *recent* evidence of Docker access (another docker-volume source of the same agent reported contact); otherwise they stay `planned`, or — with the operator's explicit `confirmDockerAccess` — ONE canary is created first and the rest follow once the agent keeps reporting; a canary that gets no agent contact for 3 minutes is rolled back. A stalled agent that owns docker-volume members shows ONE "Agent poll failing: <source>" blocker per stack (other affected stacks listed). Honest limit: the dashboard cannot tell a poll-aborting ping from an agent that is simply down.
- **Probes** come from what the dashboard already receives (`databases.last_contact` is set only when the ping succeeded): `readable` / `unreadable`, trusted for 10 minutes. `sqlite` ping is always true, so a sqlite member is never "readable" by ping (a test backup proves it, W12). The agent *inspect* probe for local images / privileged containers is **not** possible without an agent change (R1 agent unchanged): deferred to the R2 agent channel (W15) or tier-2 compose.
- Tests: `pnpm test:fork materialize` / `w10`; live (`FORK_LAB=1 W10_LAB_DATABASE_URL=… W10_LAB_DIR=… pnpm test:fork w10-lab`, recipe in the test header) runs the real code against the lab dashboard database and the real agent.

## Stack runs, RecoveryPoint and retention (W12)
A **run** backs a stack up as a group: the dashboard-held schedule (D14, `fork_stack_policy.schedule`, timezone aware) or an operator's "Back up now" starts it, every `active` member source gets one upstream `backups(status='waiting')` row **in the same step** (the exact statement and guards of upstream's bulk backup, copied into `src/fork/upstream/backups.ts`), a tracker polls the upstream statuses (no upstream hook), and a finaliser turns the result into ONE **RecoveryPoint**. Code: `src/fork/runs/` (engine, scheduler, start, steps, reauth, service, job), `src/fork/recovery-point/` (pure `decide`/`build`/`retention`, `finalize`, `prune`, `hash`), migration `0006_stack_runs`, actions `src/fork/actions/stack-run.action.ts`, UI `ui/stacks/{run-panel,run-controls.client}`.
- **Honest RecoveryPoint (D43/D39/D32/EU-04):** a complete, encrypted, checksummed run with a complete validator report ends **`pending_verification`** (UI "Backed up · verifying"); **no code path writes `verified`** (W14's verify job only, `w12-runs-static`). Validator blocked ⇒ the run still captures everything readable and finalizes `incomplete(validator_blocked)` + a `run.blocked` event. A member failed/skipped but something was captured ⇒ `incomplete(member_failed)`; stuck timeout / nothing captured / cancelled ⇒ `failed(...)`; nothing queued ⇒ `failed(run_not_started)`. An unencrypted archive (`.enc` suffix AND encryption on) or a missing checksum can never be `pending_verification`. The agent reports no checksum: the dashboard streams each archive object back and records its SHA-256 (cap `FORK_RUN_HASH_MAX_MIB`, timeout, the object must be at least as large as the size the agent reported — the agent reports the size BEFORE encryption, the stored object is larger by its header and tags, ≈ 122 bytes in the lab — 3 attempts); a restic artifact is identified by its snapshot id.
- **Durable step engine (ARCH-13, `runs/engine.ts`):** refresh inventory → validate → trigger → track → hash → finalize, state persisted on the run row after every step (a crash resumes; handlers are idempotent). At most ONE active run per stack and one row per scheduled slot are enforced by the database (double trigger ⇒ one run).
- **Schedule (ARCH-17/ARCH-10):** due-ness from the DB (`last_scheduled_at`, activation time); after downtime ONE decision for the latest slot; a due slot may start up to `FORK_RUN_CAPTURE_WINDOW_MINUTES` (60) late (waiting for capacity), later it is a **missed** slot; a slot while a run is active is skipped (**overlap**, never queued). Skips are rows + audit + an alert, never a silent gap. Capacity: `FORK_RUN_MAX_PER_AGENT` (1) / `FORK_RUN_MAX_PER_ORG` (3) concurrent runs.
- **Mandatory stuck timeouts:** `waiting` > `FORK_RUN_WAIT_TIMEOUT_SECONDS` (600) ⇒ "Agent did not start the backup within 10 min" and the waiting row is cancelled; `ongoing` with no progress > `FORK_RUN_STALL_TIMEOUT_SECONDS` (1800) (the agent bails when the per-source lock is held); hard cap `FORK_RUN_MAX_SECONDS`. Progress evidence = upstream row/storage `updated_at`.
- **F7/D31 re-authorization at every run:** the activating user's CURRENT rights (system admin capability, upstream-equivalent agent ACL, encryption still on, channels still usable) are re-checked from the database; a failure pauses the policy (facet 6), audits, queues one alert and creates no run. Only an authorized re-activation clears the pause.
- **D33 retention:** pure selection (`selectRetention`: newest verified never pruned, `keep_last`, GFS in the schedule timezone, last verified per channel kept, only-backup kept while nothing is verified, in-use RPs kept, non-verified RPs by age 30 d) executed through the upstream delete service; a failed delete ⇒ `incomplete(retention_partial)` and retried, never reported deleted. Orphan member backups (no RP) go by age. Hourly, authorization `repository.prune`.
- **Degraded mode (ADR-010):** the job is on the **runtime plane**: scheduled runs, finalisation and retention keep running while the self-check fails; discovery refresh is config-plane (not attempted when locked, said so on the run).
- Manual: "Back up now" / "Run first backup" need `backup.run` (org owner/admin), resource-scoped, rate limited, audited; cancel = same. Knobs (operator env, all with defaults): `FORK_RUN_TICK_SECONDS` 15, `FORK_RUN_WAIT_TIMEOUT_SECONDS`, `FORK_RUN_STALL_TIMEOUT_SECONDS`, `FORK_RUN_MAX_SECONDS`, `FORK_RUN_CAPTURE_WINDOW_MINUTES`, `FORK_RUN_MAX_PER_AGENT`, `FORK_RUN_MAX_PER_ORG`, `FORK_RUN_HASH_MAX_MIB`, `FORK_RUN_HASH_TIMEOUT_SECONDS`.
- Tests: `pnpm test:fork runs` (pure core, UI, static guards, contract pins; integration on Postgres 17: `w12-runs-run|schedule|reauth|retention|actions`); live (`FORK_LAB=1 … pnpm test:fork w12-runs-lab`, recipe in the test header).

## Signed manifest, verify job, key custody and the recovery kit (W14, M2 gate)
- **Verify job (`src/fork/verify/`, task `fork-verify`, runtime plane):** the only code that writes RecoveryPoint status `verified` (D43). For each archive artifact it downloads the stored object, decrypts it server-side (agent format v1), checks the gzip stream and the tar structure and records plaintext SHA-256 + size; a restic artifact must open. Integrity failures (truncated, bad tag, broken gzip/tar, size different from what the agent reported before encryption, unencrypted) make the RP `failed` with a plain reason; unreadable storage is retried (`FORK_VERIFY_MAX_ATTEMPTS`, default 5) and only then `failed`; a vanished object downgrades the RP to `incomplete`.
- **Signed manifest (`src/fork/manifest/`):** canonical JSON + detached RSA-SHA256 signature by the dashboard key (`server_private.pem`), stored as ONE restic snapshot per RP in every channel holding an artifact (`<folder>/fork-manifest/<stackId>`, password `HKDF(master, "portabase-fork/manifest/v1/<stackId>")`), read back and re-verified before the RP is promoted. Verify offline: restore the snapshot with plain `restic`, then `openssl dgst -sha256 -verify pub.pem -signature manifest.json.sig manifest.json`. Trust anchors (`fork_trust_anchor`) keep every public key that ever signed.
- **Retention coherence (`recovery/coherence.ts`):** fork artifact presence follows upstream (`backup_storage.presence`, deleted rows, failed status); incoherent RPs are downgraded (D32), expired RPs get their manifest snapshots forgotten.
- **Recovery kit (`src/fork/kit/`, page `/dashboard/integrations/recovery-kit`):** system administrator only, account-password step-up, audited, single-use grants; the kit is delivered once by `POST /api/fork/kit/<paper|digital>` (session only, `no-store`, never through API keys/MCP). Paper = base32 groups with line checksums, digital = `PBKIT1` (scrypt + AES-256-GCM). The dashboard stores a one-way verification code (not printed on the kit); the operator enters the code printed by the offline verifier (`portabase-recover verify-kit`, W14b). Until verified, stacks with an active policy read "Recovery kit not verified" and a banner shows on the Stacks page.
- **KEK rotation** (`kek-rotation.ts`): new key + re-encrypt of every registered envelope column; old keys stay. **D40:** declare which existing PostgreSQL source backs up the dashboard database; the page evaluates it (schedule, last success, channel not local, not shared with another host).
- Knobs: `FORK_VERIFY_TICK_SECONDS`, `FORK_VERIFY_MAX_MIB`, `FORK_VERIFY_DOWNLOAD_TIMEOUT_MINUTES`, `FORK_VERIFY_MAX_ATTEMPTS`, `FORK_KIT_UNVERIFIED_HOURS`, `FORK_KIT_WATCH_MINUTES`. Key custody and rotation: ADR-013; runbook: ADR-006 (vault). No upstream file is edited.

## `portabase-recover` CLI and the "My server died" guide (W14b)
- **What it is:** a dashboard-independent, hardened bash tool (`scripts/fork/recover/portabase-recover`) plus two single-file Python helpers (`decrypt-archive`, `kit-tool`; python3 + python3-cryptography, python3-yaml for the compose scan). Subcommands `plan` (default, read-only; `--deep` downloads and checks every archive), `verify-kit` (D41: offline, opens a manifest repository with the kit and prints the verification code that the operator types into *Integrations → Recovery kit*), `list`, `restore --yes`. Bare host with OpenSSL ≥ 3, restic, rclone, jq, docker + compose ≥ 2.24 is the supported path; the guide is `scripts/fork/recover/my-server-died.md` (linked from `--help` and `kit.json.recover.guide`).
- **Trust chain:** kit → manifest repo password (HKDF, in Python, never on argv) → manifest snapshot → `openssl dgst -sha256 -verify` with the kit's key (kid ↔ SPKI fingerprint checked; paper kits trust the typed fingerprint and read the PEM from storage only if it hashes to it) → strict `jq` schema + allow-list validation of every manifest string → binding (stack, RP, tag sequence, `--min-sequence` floor) → per-artifact ciphertext SHA-256 → `decrypt-archive --expect-sha256 --expect-size --audit-tar` (AES-GCM tags, `gzip -t`, plaintext hash + size, tar audit) → only then does anything touch the host. Signature / checksum / authentication failures are hard stops (exit 3), no flag overrides them.
- **Restore order:** files and folders (`<root>/files/<original path>`), Docker volumes (helper container, audited tar, compose labels), compose raw-YAML read-scope check (`env_file`/`include`/`extends`/`secrets`/`configs` outside the root are refused BEFORE rendering, not overridable), merged `docker compose config` vs `src/fork/policy/compose-deny.json` (default refuse; `--allow-privileged=<svc>` or typed `ALLOW <svc>` per service), PostgreSQL dumps (`-Fc` and `-Fd` both; sniffed, compared to the signed manifest, restored with the engine's own `pg_restore` inside the stack's database container), `docker compose up`, then the checklist, "re-attach backups" and "revoke the old agent" steps. Deviation from §4.3 text: the policy check runs BEFORE any container or volume exists (the database restore needs a running engine, and nothing from an untrusted compose file may start before it passed).
- **Untrusted archives (`decrypt-archive --audit-tar`):** no absolute names, `..`, control characters, writes through symlinks, hard links to anything but earlier regular members, devices/fifos/sparse files, setuid/setgid/sticky bits; entry/depth/name limits; inflated-size bomb guard (free disk space). Other engines (MySQL, Mongo …) are unpacked to `<root>/databases/<name>` and reported, not restored; SQLite files are unpacked there too (the manifest does not record their original path).
- **Tests:** unit `decrypt-archive*`, `w14b-kit-tool` (vs the real W14 producers), `w14b-recover-static`; shell tests `bash scripts/fork/recover/tests/run.sh [group]` (real restic repos on a local rclone remote, signed with per-run test-only keys; groups `static usage happy mutation injection compose full`); CI job `recover-cli` (ShellCheck + shell tests); lab drill `dev/fork-lab/drills/recover-drill.sh` (`FORK_LAB=1`).

## Compose policy (D27, W20a)
- **What it is:** a pure TypeScript policy engine for the restore ("disaster") profile in `src/fork/policy/{rules,raw,engine,approval}.ts`. It never runs compose and does no I/O: callers hand it text. `checkRawCompose` checks the RAW compose/override YAML before anything is rendered (every `env_file` / `include` / `extends.file` / `label_file` / `secrets.*.file` / `configs.*.file` target must stay inside the restore root, recursively through included/extended files; SEC-17 size/depth/node/alias limits, one document, no duplicate keys or custom tags). `evaluateRenderedCompose` evaluates the `docker compose config --format json` bytes returned by the restore-target agent (D46) against the ONE shared rule file `compose-deny.json` (v2) and returns `allow | deny | needs-explicit-override` with rule ids and plain-language text, never a value. `buildPolicyApproval` / `checkPolicyApproval` issue and re-check a per-service approval (`ALLOW <service>`) bound to the SHA-256 of the exact rendered bytes, the rule set, the roots and the stack / recovery point / agent.

- **Hard refusals** (never overridable; not even representable in an approval): read-scope violations, ambiguous paths (`..`, `$`, `~`, relative, `//`), invalid / oversized YAML or JSON, unknown top-level keys, malformed shapes. **Overridable per service:** the 8 D27 rules plus `shared_namespace` (`container:` joins) and `unknown_directive` (any service key not in the allow-list, odd volume drivers, `security_opt` other than no-new-privileges, ...). v2 closes bypasses of the W14b list: named volume bound to `/etc` via `driver_opts`, external network named `host`, `use_api_socket`, `volumes_from`/`pid: container:`, GPU `deploy` devices, `..` in agent-returned paths, includes not scanned recursively.
- **Kits:** since W28 the recovery kit and the bare-host guide pin the CLI at tag `fork/w27a-done` (rule file v2 + the F-01 realpath gate). Kits issued before W28 keep naming the older `fork/w14b-done` (rule file v1, weaker) until the owner re-issues them; `fork/w14b-done` is never moved.
- **Tests:** `pnpm test:fork compose-policy` (needs `jq` and `python3-yaml`); lab check `FORK_LAB_COMPOSE=1 pnpm test:fork:unit compose-policy-engine` renders `dev/fork-lab/demo-stack` locally (reads files, starts nothing); `bash scripts/fork/recover/tests/run.sh compose` for the CLI fixtures.

## Mirror compiler (W20, R3 — library only)
- **Input → output:** `src/fork/compose-compiler/` takes the *policy view* of a rendered compose project (the value-free JSON the target agent already uploads) and returns a value-free, hash-bound `MirrorSpecV1` (full structural skeleton of the mirror project + one action per environment key) and a redacted, readable diff (`renderMirrorDiff`: keys, names, ports and counts, never values). The dashboard never sees a value.
- **No overrides in mirror mode:** every W20a engine hard refusal and every finding (privileged, host namespaces, devices, `docker.sock`, binds outside the workspace, unknown directives) is a refusal. There is no `ALLOW <service>` for mirrors. Unknown keys fail closed.
- **Isolation by construction:** no published port except one loopback port (`127.0.0.1:<host_port>`, private access); every mirror network is `internal: true` (plus one `pbm_access` network for the access service); no external network, volume or secret; no host path outside the workspace; one Compose project `pbm-<name>`.

A wrong guess makes the mirror fail its health gate, never run unsafely. `options.env` is the per-app override hook (`keep_exact` is audited and listed in `kept_production_secrets`).
- **Not shipped yet:** the runner-side apply (`applyMirrorSpec` is the TypeScript reference + `compose-mirror-vectors.json`; the Rust port and the `docker compose config` validation are follow-up W20-f1), the runner (W21), the mirror model and UI (W22a/W22b). Nothing starts a mirror today.

## Restore orchestrator (W18a, backend only)
- **What it is:** `src/fork/restore-run/**` executes ONE hash-bound W16 plan on the TARGET agent through the W17 task types, on the W12 step engine. Server actions only (`src/fork/actions/restore-run.action.ts`: start, approve policy, cancel, cleanup, view, list); **no UI and no API route yet** (wizard = W18b). Tables: `fork_restore_run` (state + W12 `steps`) and `fork_restore_run_task` (step journal, written in the enqueue transaction), migration `0014_restore_run`.
- **Steps (derived from the plan):** `verify_manifest` (dashboard; signed manifest vs trust anchors and the plan's bound hash, BEFORE any task) → `probe` → `stage` → `apply` → [`render` (+ policy gate) → `restore_db` → `compose_up` → `check_services`]. The bracket only exists for plans with a `compose_up` action. One agent task per step, enqueued only after the previous step finished.
- **States:** `running`, `awaiting_approval` (a flagged service needs `ALLOW <service>` from a `restore.production.approve` holder), `succeeded`, `incomplete` (data restored but a service is not running), `failed` (`reason` + `failed_step`), `cancelled`. `verification` is `started` (every rendered service reported running right after `compose up`) or `data_only`. **It never says "tested" or "verified"**: a restore is only proven by a DR drill (W19) or the scheduled data-only test restore (W-TR).
- **Guards:** typed confirmation `RESTORE <project>` bound to the plan hash when the target is a production host; one active run per target agent; a plan runs at most once (retry = new plan); `existing_stack` in-place restore stays refused (#145); every tick re-checks the STARTER's current rights (no service account); a run is capped at `FORK_RESTORE_RUN_MAX_HOURS` (default 12). `FORK_RESTORE_TICK_SECONDS` (default 10) sets the job period; **`0` = this process never ticks: live lab only**.
- **Cleanup is explicit** (`cleanupRestoreRun`, only for failed / cancelled / incomplete runs): the agent removes only what carries this restore id AND its own agent id; foreign look-alikes are kept. Nothing is cleaned automatically.
- **After a successful dashboard restore re-attach backups on the new machine by hand** (guide Part 5, `scripts/fork/recover/my-server-died.md`, "Protect the new machine again"). An "Adopt restored stack" action is deferred (follow-up W18a-f1).
- **Known residuals:** the agent leaves consumed PostgreSQL archives in `<workspace>/.portabase/stage/` after a successful restore (follow-up W18a-f3, agent change); "verified by probe" needs an agent probe extension (W18a-f2); one-shot services that exit 0 make a run `incomplete` by design.

### Scheduled data-only test restore (W-TR, D36 / D44)
Production data reaches a test host only for a data-only test restore to a host an admin marked as test, and is wiped afterwards.
- **What it does:** per stack, on a schedule held by the dashboard (`fork_test_restore_schedule`, default disabled), the latest `verified` recovery point is restored data-only into `<restore root>/<project>-test-restore/scratch` on an agent whose environments are ALL `host_role = test`: signed manifest → checksums → `gzip -t` + plaintext hash/size (agent `restore_stage`) → engine integrity check in a no-network helper container (`restore_verify`: sqlite `PRAGMA integrity_check`, PostgreSQL `pg_restore -f /dev/null`) → **verified wipe** (cleanup, then an independent probe must report the workspace `absent`). The app is never started; "App start-tested" is never set (R3).
- **Facet:** "Data verified by test restore · N d ago" needs a succeeded, `data_verified` run AND a verified wipe; it turns "Out of date" after the per-stack decay age (default 14 d, env `FORK_TEST_RESTORE_STALE_DAYS`) and raises `stack.test_restore_stale`. A failed run never refreshes it. A failed wipe blocks further test restores of the stack until a verified wipe ("Wipe now").
- **App start-tested (R3, ADR-016)** is a different, later facet: it needs a mirror revision that reached READY on a runner; a test restore never sets it.
- **Personal data (D44):** a stack not declared `contains_personal_data = false` needs the explicit per-stack opt-in (`setStackPrivacy`); undeclared counts as personal data.
- **R3 (test mirrors, ADR-009):** a mirror holds a copy of production data only on a host an admin marked as `runner`; it never leaves that host and needs an explicit per-stack opt-in when the stack contains personal data.
- **Agent:** capability `test-restore.v1` (image needs `sqlite3` + `pg_restore`); ADR-007 A16. DBMS without a checker (MySQL/MariaDB/Mongo/MSSQL) are counted "not engine-checked", never hidden.
- **Lab:** `FORK_LAB=1 FORK_TEST_DATABASE_URL=… W17_AGENT_IMAGE=portabase-agent-fork:wtr-lab WTR_EVIDENCE_DIR=… pnpm exec vitest run --project e2e wtr-test-restore-lab` (after `pnpm build`). The dashboard child runs with `FORK_TEST_RESTORE_TICK_SECONDS=0`; the test process drives the scheduler / run / wipe ticks.
- **Not yet:** the Schedule-tab panel (W-TR-f1, #159); configure via the server actions in `src/fork/actions/test-restore.action.ts` until then.

## Mirror runner + isolation probe (W21, R3, [ADR-008](vault `ADR/ADR-008-mirror-runner.md`))
- **What it is:** an agent-level *designation* (`fork_runner`, migration `0017_runner`; `host_role` is unchanged) of a dedicated host that will only ever run test mirrors. Eligible only with the owner's designation (system admin, password step-up, audited) **and** an enrolment that reports `runner.v1` **and** no Arcane environment **and** no upstream database. No row = not a runner.
- **Agent side** (`portabase-agent`, `src/fork/runner/`): `FORK_HOST_ROLE=runner` reports exactly `channel.v1, noop.v1, channel-maint.v1, runner.v1` and never enters the restore / quiesce init (the master key is not loaded into fork state). It refuses every non-runner task with `role_forbidden`; every other agent refuses runner tasks the same way.
- **The probe (`runner_probe`):** a hardened helper on a fresh *non-internal* pool network tries the configured production targets (database / SMTP / webhook / storage IPs, the dashboard and Arcane hosts, DNS over TCP and a DNS name) and reports `blocked | reachable | error` per target. The dashboard decides (`evaluateProbe`, fail closed: stale, changed targets, unknown or missing ids, any `error`, a failing own-name DNS all read *not isolated / unknown*). `assertRunnerReady` is the gate W22a calls before a mirror may become READY.
- **Enforcement is the host firewall, not `internal: true`:** the runbook (nftables deny-by-default incl. DNS, `daemon.json`, quotas) is `dev/fork-lab/runner/` + ADR-008. The lab (`dev/fork-lab/runner/runner.sh`, a docker-in-docker "runner box") emulates the VM; **real-VM proof is pending (#125)**.
- **Flag:** all runner services refuse with `mirrors_disabled` unless `FORK_MIRRORS_ENABLED=true`.
- **Known residual:** the runner agent still holds the raw instance master key (recorded, ADR-008 §8).
- **Tests:** `pnpm test:fork:unit w21-runner`, `pnpm test:fork:integration w21-runner`; lab (`FORK_LAB=1 W21_AGENT_IMAGE=… pnpm test:fork:e2e w21-runner-lab`, needs `pnpm build`, docker and Postgres); agent: `cargo test --features fork-stacks fork::runner`.

## Test mirrors — model, state machine, orchestration backend (W22a, R3, backend only)
Behind `FORK_MIRRORS_ENABLED` (default off). A **test mirror** of a stack is created from a **verified** recovery point on a **designated, isolated runner** ([W21](#mirror-runner--isolation-probe-w21-r3-adr-008-vault-adr-adr-008-mirror-runnermd)). W22a is the dashboard backend only: the wizard (W22b), list/detail pages and banner (W23) and the runner-side engine (W22a-f1, agent repo) are **not** part of it. The agent engine (`mirror.v1`, W22a-f1, agent repo) now exists: **Flow D lab** (`dev/fork-lab/runner/w22a.sh` + `src/fork/__tests__/e2e/w22a-mirror-lab.test.ts`, `FORK_LAB=1`, docker-in-docker runner box, local agent image, run twice 9/9) created a READY mirror of the demo stack through `createMirror`, proved isolation from inside the mirror, loopback-only access, secrets custody, limits, role gating, blocked / cancelled / firewall-off revisions with verified wipes. Real-VM proof (#125) is PENDING-HUMAN; the master key is loaded on a mirror-enabled runner (ADR-008 §12 residual, #201). The wizard (W22b) and list/detail pages (W23) are still to come.
- **Model** (migration `0018_mirror`): `fork_mirror` (a named mirror), `fork_mirror_revision` (one creation attempt; its id is the restore id sent to the runner), `fork_mirror_event` (timeline), `fork_mirror_task` (step journal written inside the enqueue transaction); `fork_stack.mirror_opt_in_at/by`; the plan purpose CHECK now allows `mirror`. Everything stored is ids, names, codes, hashes, counts, ports and the value-free W20 spec — no env value, secret, URL or host IP.
- **Planner**: purpose `mirror` (plan v2, `PLAN_VERSION` 2, ruleset `w16.2`; stored v1 plans turn `stale: plan_version` once). Runner-only, mode `new_stack`, no approvals; whatever would need approval blocks the plan instead. A mirror plan can never start a restore run.
- **State machine** (`src/fork/mirror/machine.ts`): `requested → planning → validating → staging → restoring_files → transforming → restoring_db → starting → healthchecking → ready`, any active state → `blocked | failed | cancelled`. Order differs from plan v1.1 §8.3 (files → transform → DB) because the DB restore runs inside the transformed project. `blocked` = the input can never succeed without an operator change (planner blocker, compile refusal, unconfirmed kept secret, runner ineligible); `failed` = a run-time failure. Every non-ready ending gets an **automatic verified wipe** (`mirror_wipe`, then an independent `mirror_probe` must report the workspace absent).
- **READY needs five gates** (ADR-016): `expected_data`, `db_health`, `app_smoke`, `isolation` (a probe enqueued by THIS revision after the step started, ≥ 1 admin probe target), `side_effects` (final view checked by the W20 invariants with owner labels and per-service `mem_limit`/`pids_limit`/`cpus`). READY and the start-tested fact are one row (`startTestedFact`). "Start-tested" is not "restore-tested" and not "verified".
- **Access**: loopback only (`127.0.0.1:<port>` on the runner, range 41000–41999) + SSH-tunnel hint, ready mirrors only, audited. No proxy.
- **Env**: `FORK_MIRROR_ROOT` (default `/srv/portabase-mirrors`, must equal the agent's), `FORK_MIRROR_MAX_HOURS` (1–24, default 4), `FORK_MIRROR_TICK_SECONDS` (0–300, default 10; 0 = never ticks: lab only).
- **Actions** (`src/fork/actions/mirror.action.ts`): `setStackMirrorOptInAction` (system admin + org admin), `previewMirrorPlanAction`, `createMirrorAction`, `cancelMirrorRevisionAction`, `retryMirrorWipeAction`, `getMirrorViewAction`, `getMirrorAccessAction`. Create needs `mirrors.manage` on the stack, the privacy acknowledgement for personal data, typed `KEEP svc.KEY` per kept production value and a runner isolated within 24 h.
- **Contract**: nine `mirror_*` task types (capability `mirror.v1` + `runner.v1`), payload/result schemas in `src/fork/mirror/payload-schema.ts`, cross-language vectors in `__tests__/fixtures/restore-task-vectors.json` (`mirror` section, 56 codes).
